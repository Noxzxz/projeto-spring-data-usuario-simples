### T1.1 - Entidades DDD com Herança JPA + Value Objects
--------------------------------------------------------------------------------
Status:         NÃO INICIADA (implementação atual NÃO segue DDD)

Evidências:
  - ENTIDADE Usuario.java existe, MAS:
    * NÃO há classe abstrata Pessoa como base
    * NÃO há @Inheritance(strategy = InheritanceType.JOINED)
    * NÃO existem entidades Aluno, Professor, Administrador
    * Atributos são primitivos (String senha), não usam VOs
    * Long id em vez de UUID
  
  - Value Objects EmailUsuario, NomeUsuario, SenhaCriptografada existem como:
    * records Java (correto)
    * MAS NÃO SÃO USADOS pela entidade Usuario
    * Usuario usa String direto para email, nome, senha
  
  - AlunoRepository NÃO existe
  - TiposAssinatura enum existe, mas não integrado com Aluno

Problemas:
  [CRÍTICO] Usuario é uma entidade anêmica, não um Aggregate Root
  [CRÍTICO] Não há separação entre Aluno/Professor/Admin - todos são "Usuario"
  [CRÍTICO] VOs existem mas não são usados nas entidades
  [CRÍTICO] Herança JPA não implementada
  [CRÍTICO] UUID não usado - sistema usa Long (sequencial, não seguro)

Arquivos relacionados:
  - src/main/java/.../domain/Usuario.java (entidade anêmica)
  - src/main/java/.../domain/vo/EmailUsuario.java (não usado)
  - src/main/java/.../domain/vo/NomeUsuario.java (não usado)

# PROBLEMAS ARQUITETURAIS
================================================================================

1. ARQUITETURA DDD NÃO IMPLEMENTADA
   - Planejamento exige: domain, application, infrastructure, interfaces.rest
   - Implementação atual: controller, service, repository, domain (misturado)
   - Não há separação de responsabilidades
   - Entidades são anêmicas (sem lógica de domínio)

2. PACOTE infrastructure NÃO EXISTE
   - Sem infrastructure.security (JwtAuthFilter, SecurityConfig)
   - Sem infrastructure.persistence.jpa (implementações de repositório)
   - Sem infrastructure.messaging (notificações)

3. PACOTE application NÃO EXISTE
   - Sem UseCases (ConcluirModuloUseCase, MatricularAlunoUseCase, etc.)
   - Lógica de aplicação está em Services (camada de serviço anêmica)

4. DOMÍNIO ANÊMICO
   - Entidades são DTOs com getters/setters
   - Sem métodos de domínio (podeAvancarModulo, concluir, verificarAprovacao)
   - Regras de negócio no controller/service, não na entidade

5. VALUE OBJECTS NÃO USADOS
   - EmailUsuario, NomeUsuario, SenhaCriptografada existem
   - Entidade Usuario usa String direto para email, nome, senha
   - VOs deveriam ser os tipos dos atributos

6. SEM EVENTOS DE DOMÍNIO
   - CursoConcluídoEvent não existe
   - Sem @EventListener para gamificação
   - Acoplamento direto entre contexts (quando existir)

7. SEM SEPARAÇÃO DE BOUNDED CONTEXTS
   - Todo código em único pacote: com.exemplo.usuariosimples
   - Deveria ter: usuario, academico, gamificacao, financeiro, engajamento
   - Contextos misturados impedem evolução independente

8. LONG EM VEZ DE UUID
   - Entidades usam Long id (sequencial, inseguro)
   - Planejamento exige UUID para todos os aggregates
   - Aluno deveria ter id UUID

9. SEM SEGURANÇA
   - spring-boot-starter-security não está no pom.xml
   - Senhas em texto puro
   - APIs públicas sem autenticação

10. FRONTEND MAIS AVANÇADO QUE BACKEND
    - Angular tem models ricos, serviços completos
    - Backend não responde endpoints esperados
    - Inconsistência gera erros em produção
